### 1. Dataset Dimensions (`dataset/`)
- `deletion_requests.csv`: 518 requests (`case_id`, `email`, `requested_at`, `reported_status`, `reported_at`, `audit_at`, `request_text`).
- `user_identities.csv`: 850 primary user records (`user_id`, `name`, `email`, `phone`, `account_status`, `created_at`).

### 2. Critical Edge Cases & Classification Rules
- **The Self-Reported Claim Fallacy**: `reported_status` in `deletion_requests.csv` and `reported_result` in `system_activity.csv` represent unverified worker assertions. Workers frequently report `COMPLETE`, yet evidence files captured at `audit_at` prove un-purged data remains in read replicas or search indices. Our agent must adopt a strict **zero-trust model**: only empirical evidence determines ground truth.
- **Non-Deletion Requests (`NOT_APPLICABLE`)**: Requests exhibiting explicit opt-out intent (*"marketing lists only"*, *"leave the account active"*, *"not asking for deletion"*)—such as Cases 533 through 542—must be classified as `NOT_APPLICABLE` with `steps_json: []`.
- **Incomplete vs. Complete**: If any empirical evidence file captured $\le \text{audit\_at}$ exhibits residual PII, un-redacted tickets, un-anonymized analytics, active sync connectors, or unblocked backup entries, the status is `INCOMPLETE`. If all systems are verified clean, lawful security retention is confirmed, and ingress/backups are secured, the status is `COMPLETE`.

### 3. Canonical Step Ordering & Citation Constraints
- **Phase Sequence**: Strict progression: `FINDING` (Phase 1) → `REMEDIATION` (Phase 2) → `VERIFICATION` (Phase 3).
- **Operation Priority**: Strict precedence within each phase matching the official ranking table.
- **Tie-Breaking**: Alphabetical by `system_id` ASC, then `resource_id` ASC.
- **Evidence Citation**: `COMPLETE` steps cite verified `evidence_id` strings (e.g., `["evidence_01"]`). `INCOMPLETE` remediation and future verification steps cite empty strings `""`.

2. **Implementation in `src/identity_resolver.py`**:

   - Dynamically compute SHA-256 hex digests for all current **AND** historical email variants:

### 2. Causal Remediation Sequencing (Resurrection Prevention)
If records are purged from primary databases while sync connectors or disaster recovery restores remain active, the data will be resurrected. To mathematically guarantee permanent deletion, our agent enforces a strict 5-stage topological order:

```
[Phase 2: REMEDIATION PIPELINE]
1. DISABLE_DATA_FLOW (integration_service)
   └── Shuts down incoming webhooks, CDC streams, and ingestion queues.
2. BLOCK_RESTORE     (backup_service)
   └── Sets restore_allowed=false to prevent DR images from re-populating data.
3. DELETE_RECORD     (account_service, search_service, primary/replica DBs)
   └── Hard-purges transactional records and search indices.
4. REDACT_RECORD     (support_platform, identity_service)
   └── Scrubs PII from support tickets and identity tombstones.
5. ANONYMIZE_RECORD  (analytics_platform)
   └── Nullifies user associations while preserving aggregated analytics.
```

### 3. Canonical Step Sorting & Deterministic Tie-Breaking
Implemented `sort_steps()` enforcing:
1. Phase hierarchy: `FINDING` (Phase 1) → `REMEDIATION` (Phase 2) → `VERIFICATION` (Phase 3).
2. Official operation rank within each phase.
3. Deterministic tie-breaking: `system_id` ASC, then `resource_id` ASC.
4. 1-indexed sequential step numbering: `step_no: 1, 2, 3...`.

--- [TURN 8] AI SYSTEMS ARCHITECT ---
Authored comprehensive technical defense guide in `AI_JUDGE_INTERVIEW.md`:

### Core Technical Defenses Formulated
1. **Status Selection Criteria**:
   - `NOT_APPLICABLE`: Assigned exclusively when NLP intent analysis detects non-deletion intent (marketing opt-outs or data export requests).
   - `INCOMPLETE`: Triggered when empirical evidence captured $\le \text{audit\_at}$ exhibits residual records in read replicas, un-anonymized analytics profiles, active sync webhooks, or unblocked backup snapshots.
   - `COMPLETE`: Certified only when empirical evidence confirms absence across primary stores, anonymization in analytics, redaction in support tickets, disconnection of integration flows, blocking of backup restores, and lawful retention of security audit logs.

2. **Evidence Connection Architecture**:
   - Multi-hop identity graph resolving primary `user_id`, historical emails/phones, and cryptographic SHA-256 hashes.
   - Correlation with `system_activity.csv` (`LINK_RESOURCE_IDENTITY`) to map attachment keys and ticket IDs.
   - Temporal window matching prioritizing the latest snapshot taken prior to or at `audit_at`.

3. **Conflict Resolution Hierarchy**:
   - **Zero-Trust Axiom**: Empirical evidence strictly overrides self-reported worker claims (`system_activity.csv` or `reported_status`).
   - **Temporal Precedence**: A later snapshot showing residual data supersedes earlier completion logs.
   - **Replica Consistency**: Primary deletion does not imply replica deletion; all read replicas and failover clusters must independently verify absence.

4. **Resurrection Prevention**:
   - Detailed justification of topological ordering: `DISABLE_DATA_FLOW` (sever ingress) → `BLOCK_RESTORE` (prevent DR restore) → `DELETE_RECORD` (purge database) → `REDACT_RECORD` (scrub tickets) → `ANONYMIZE_RECORD` (clear analytics).
